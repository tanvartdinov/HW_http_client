# Домашнее задание «Надёжный клиент афиши мероприятий»

## Ситуация и цель

Редактор городской рассылки выбирает события для читателей. Ему нужна консольная программа: найти мероприятия по названию и категории, посмотреть сведения об одном событии и сохранить подборку в JSON. Источник — учебный сервис «Афиша мероприятий».

Сервис иногда недоступен, отвечает с задержкой или возвращает некорректные данные. Ваша программа должна отличать эти случаи от пустой подборки, ограничивать повторные запросы и выдавать понятное сообщение.

В результате вы создадите собственный HTTP-клиент с Session, тайм-аутами, ретраями и доменными исключениями, проверите контракт JSON и подключите клиент к CLI. Структуру проекта, границы try/except, иерархию исключений, внутреннюю модель результата и оформление отчёта выберите самостоятельно.

## Что вы получаете

- `service/` — готовый FastAPI-сервис, 36 вымышленных событий мая 2027 года: по 12 каждой категории.
- `CONTRACT.md` — контракт API и описание учебных маршрутов.
- `fixtures/` — HTTP-ответы в JSON-конвертах и последовательности ответов для проверок.
- `requirements-student.txt` — закреплённые версии библиотек клиента.
- `service/app/static/dynamic.html` — дополнительная динамическая страница для бонуса с Playwright.

Клиента и готового решения в комплекте нет. Создайте отдельный Git-репозиторий. Сервис можно хранить рядом с ним; переписывать сервер для обязательной части не нужно.

## 1. Запустите сервис

Нужен Python 3.11+; рекомендуем Python 3.12. Распакуйте архив и откройте терминал в папке `homework-afisha/service`.

Windows:

```powershell
py -3 -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
.venv\Scripts\python.exe -m uvicorn app.main:app --reload
```

macOS / Linux:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m uvicorn app.main:app --reload
```

Оставьте сервер работать в этом терминале. Афиша: http://127.0.0.1:8000/ ; API: http://127.0.0.1:8000/api/v1/events ; документация: http://127.0.0.1:8000/docs . Swagger UI требует интернет для загрузки интерфейса, сайт и API после установки зависимостей работают локально. Остановка — Ctrl+C. Если порт занят, добавьте `--port 8001` и измените URL в настройках клиента.

## 3. Реализуйте HTTP-клиент

Клиент должен уметь получать список событий с фильтрами и одно событие по ID. Все сетевые обращения выполняйте через переиспользуемую `requests.Session`. Предусмотрите закрытие сессии и объясните в README, кто ей владеет. Создание Session внутри класса и передача снаружи одинаково допустимы.

В каждом запросе явно передавайте timeout. Настройки читайте из переменных окружения:

| Переменная | По умолчанию | Требование |
| --- | --- | --- |
| AFISHA_BASE_URL | http://127.0.0.1:8000 | HTTP(S)-адрес сервиса |
| AFISHA_CONNECT_TIMEOUT | 2 | Положительное число секунд |
| AFISHA_READ_TIMEOUT | 3 | Положительное число секунд |
| AFISHA_MAX_ATTEMPTS | 3 | Целое от 1 до 5; включает первый запрос |
| AFISHA_RETRY_DELAY | 1 | Неотрицательное число секунд между попытками |
| AFISHA_TOKEN | пусто | Необязательный токен |

Учебный сервер не требует и не проверяет токен. Если переменная непустая, клиент передаёт `Authorization: Bearer <token>`. Если пустая — заголовок не отправляется. Токен не выводится в логах и не коммитится. Для проверки заголовка достаточно тестового значения и подмены транспорта.

Пример настройки PowerShell: `$env:AFISHA_READ_TIMEOUT="1"`; macOS/Linux: `export AFISHA_READ_TIMEOUT=1`. Изменения действуют в текущем терминале. `.env.example` должен содержать имена переменных и безопасные примеры. Автоматическая загрузка `.env` не обязательна: если её добавляете, опишите механизм и зависимость.

Ошибочная конфигурация должна обнаруживаться до HTTP-запроса и завершать команду понятным сообщением.

## 4. Опишите исключения и повторы

Создайте общий базовый класс ошибок вашего клиента и различимые ошибки: тайм-аут, соединение, серверная ошибка, клиентская HTTP-ошибка, ресурс не найден, ограничение частоты, некорректный JSON, нарушение схемы. Имена и структуру наследования выберите сами. Для 404 и 429 можно использовать специализированные подклассы общей ошибки 4xx.

При преобразовании исходного исключения сохраняйте причину через `raise ... from ...`. Не выпускайте из публичных методов клиента необработанные requests-исключения или `tenacity.RetryError`. В исключении полезно хранить статус, число попыток и безопасное описание операции.

Ретрай охватывает один HTTP-запрос, а не весь CLI и не весь процесс построения отчёта. Используйте tenacity. Не включайте второй независимый механизм повторов через HTTPAdapter.

| Сценарий | Повторять? | При 3 попытках | Ожидаемый результат |
| --- | --- | --- | --- |
| 200 + корректная схема | Нет | 1 вызов | Валидные данные |
| 200 + пустой items, total=0 | Нет | 1 вызов | Успешная пустая подборка |
| Timeout | Да | Не более 3 вызовов | После исчерпания — ваша ошибка тайм-аута |
| ConnectionError при недоступном сервере | Да | Не более 3 вызовов | Ваша ошибка соединения |
| Любой HTTP 5xx | Да | Не более 3 вызовов | После исчерпания — ваша ошибка сервера |
| 500 → 500 → 200 | Да, до успеха | Ровно 3 вызова | Успешный результат |
| Timeout → 200 | Да, до успеха | Ровно 2 вызова | Успешный результат |
| 400 / 401 / 403 / 422 | Нет | Ровно 1 вызов | Ваша ошибка клиентского HTTP-запроса |
| 404 | Нет | Ровно 1 вызов | Ваша ошибка «не найдено» |
| 429, в том числе с Retry-After | Нет | Ровно 1 вызов | Ваша ошибка ограничения частоты |
| 200 + битый JSON | Нет | Ровно 1 вызов | Ваша ошибка декодирования |
| 200 + неверная схема | Нет | Ровно 1 вызов | Ваша ошибка контракта |

Все 4xx, включая 408 и 429, в этом ДЗ не повторяются. Для 429 сохраните значение Retry-After в ошибке/отчёте, но не ожидайте и не повторяйте автоматически. Это заданная политика клиента, а не универсальное правило для всех API.

Ошибки сертификата TLS, некорректный URL и ошибки конфигурации не считаются временной недоступностью; не повторяйте их. Учтите, что некоторые исключения requests наследуются друг от друга: порядок обработки влияет на результат.

Между повторными попытками делайте паузу AFISHA_RETRY_DELAY. После успеха или последней неудачи дополнительная пауза не нужна. Отразите в диагностике номер попытки и причину повтора. Тесты могут подменять ожидание, чтобы не тратить реальное время.

## 5. Проверьте данные

Порядок обработки: транспорт → HTTP-статус → JSON → контракт. Например, HTTP 500 с HTML-телом должен считаться серверной ошибкой, а не ошибкой JSON.

Обязательная валидация описана в CONTRACT.md. Не подменяйте ошибку пустым списком. Не отбрасывайте молча отдельные неверные записи: если хотя бы одна запись некорректна, весь ответ считается нарушением контракта. Дополнительные неизвестные поля допускаются.

Способ проверки выберите сами: ручная проверка, Pydantic или JSON Schema. Не допускайте незаметного преобразования `"1800"` в 1800 и `true` в 1. Поле price=0 является корректной бесплатной ценой.

## 6. Сделайте CLI и отчёт

Обязательные операции:

- `list`: поиск по названию и категории, вывод количества и списка событий.
- `show`: информация об одном событии по ID.
- `--output`: сохранение успешного результата в JSON UTF-8 с читаемой кириллицей.

Пример интерфейса ниже — ориентир, а не требование к имени пакета. В README приведите свои точные команды. Формат отчёта выбираете вы; он должен содержать статус операции, фильтры/ID, число найденных событий для списка и сведения о событиях: id, title, category, starts_at, venue, price, currency, абсолютную ссылку. Для show дополнительно нужны address, organizer, description, age_limit. Ссылку стройте на основе BASE_URL и url из API.

Успех и пустая выдача: код завершения 0. Ошибка сервиса/данных или записи файла: ненулевой код, краткая диагностика в stderr, без обычного traceback. Ошибка аргументов CLI и конфигурации тоже даёт ненулевой код. Не создавайте успешный отчёт при ошибке и не затирайте существующий файл после неудачного запроса. Покажите фактическое число попыток для диагностируемого неудачного запроса.

### Примеры при исходных 36 событиях

| Команда-пример | Ожидаемое наблюдение |
| --- | --- |
| `python -m afisha_client list --query "ДЖАЗ" --category concert --output jazz.json` | 3 события: ID 1, 10, 34; файл с успешным результатом; exit 0 |
| `python -m afisha_client list --category exhibition` | Найдено 12 выставок; exit 0 |
| `python -m afisha_client show 5` | «Тишина в кадре», price=0, бесплатно; exit 0 |
| `python -m afisha_client list --query "несуществующее-событие-xyz"` | Найдено 0; это успех, exit 0 |
| `python -m afisha_client show 999` | Понятная ошибка «мероприятие не найдено», 404, 1 попытка, ненулевой exit |

Отдельно покажите обработку 500, тайм-аута, 429, битого JSON и неверной схемы. Диагностические `/demo/...` не нужно включать в пользовательский CLI: достаточно теста или отдельного демонстрационного скрипта, который использует тот же HTTP-слой клиента. Тайм-аут проверяйте запросом `/demo/timeout?seconds=5` при read timeout=1; успешное тело этого маршрута не является EventList.

## Критерии зачёта

| Проверяем | Условие |

| Функциональность | list/show, оба фильтра, пустая выдача, экспорт JSON |
| HTTP | Одна переиспользуемая Session, явный timeout каждого вызова, корректное закрытие |

## Краткая памятка

Session хранит общие настройки и переиспользует соединения. Timeout requests ограничивает ожидание соединения/чтения, а не общее время всей программы. `raise_for_status()` проверяет 4xx/5xx, но не структуру JSON. `response.json()` может завершиться ошибкой даже при HTTP 200. `raise NewError(...) from original` сохраняет причинную связь. Retry-After может быть числом секунд или HTTP-датой; в этом ДЗ для 429 достаточно сохранить его исходное значение, автоматический ретрай запрещён. При tenacity задавайте условие повтора и предел явно; его настройки по умолчанию не являются политикой этого задания.

Справочные источники: https://requests.readthedocs.io/en/latest/user/advanced/ ; https://requests.readthedocs.io/en/latest/user/quickstart/ ; https://tenacity.readthedocs.io/en/latest/ .
