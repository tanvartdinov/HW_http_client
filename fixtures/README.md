# Как использовать fixtures

Это входные данные для тестов, не готовая реализация клиента и не отдельный сервер.

Каждый файл ответа — валидный JSON-конверт с полями status_code, headers, body_text. Тело ответа хранится строкой: так в корректном файле fixture можно описать даже синтаксически сломанный JSON. Статус и заголовки не являются полями EventList.

Сначала загрузите конверт через json.load, затем настройте подменённый HTTP-ответ: status_code, headers и байты тела body_text в UTF-8. Можно создать requests.Response, присвоив status_code, headers и _content; приватный _content допустим здесь только как техника создания тестового объекта. При необходимости укажите encoding='utf-8'. Важно, чтобы raise_for_status() и json() работали как у настоящего Response. Не возвращайте словарь-конверт из клиента как данные API.

Подмените метод, который действительно вызывает ваш клиент: Session.request или Session.get. Для серии ответов используйте side_effect. Ожидание между попытками можно подменить; проверяйте счётчик вызовов. Конкретный тестовый код напишите самостоятельно.

- 200_list.json: два валидных события, включая бесплатное; это небольшой снимок, а не весь каталог из 36 событий.
- 200_detail.json: одно бесплатное событие (ID 5).
- 200_empty.json: корректная пустая выдача.
- 400.json, 404.json, 429.json, 422.json, 500.json: соответствующие HTTP-статусы. 422.json — упрощённое тело ошибки для проверки статуса, не точная копия массива ошибок FastAPI.
- 500_html.json: приоритет HTTP-статуса над попыткой разобрать JSON.
- broken_json.json: тело не декодируется как JSON, хотя сам конверт корректен.
- bad_schema.json: валидный JSON с неверными полями.
- wrong_type.json, bool_price.json, wrong_total.json, bad_date.json: дополнительные проверки контракта.
- sequences.json: порядок ответов/исключений; имена response_file разрешаются относительно fixtures. Запись exception обозначает экземпляр указанного исключения requests, который нужно выбросить вместо HTTP-ответа. Не используйте eval для разбора имён; задайте явное соответствие.
- broken_structure.html: вход для бонусной проверки нарушения HTML-структуры.

Для каждого отдельного теста создавайте свежую последовательность и обнуляйте счётчики. После последнего элемента не начинайте последовательность заново: лишний вызов должен приводить к падению проверки.

__Дополнительная задача Retry-After__

Последовательность rate_limit_recovers в sequences.json задаёт ответы 429 → 200. При включённом режиме клиент должен выбрать задержку 2 секунды, выполнить второй запрос и вернуть успешный результат. При выключенном режиме он должен завершиться после первого ответа 429.

Для остальных сценариев самостоятельно создайте варианты ответа 429: с будущей датой, прошедшей датой, некорректным значением, отсутствующим заголовком и слишком большой задержкой.

В проверках фиксируйте текущее время, подменяйте ожидание и проверяйте как количество запросов, так и переданную длительность задержки.
